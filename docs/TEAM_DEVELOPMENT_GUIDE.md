# 1. Introduction

Welcome to the FinStack development team.

This document is the official onboarding guide for every developer working on this project. Whether you are joining during the first sprint or six months into development, this guide should be your first point of reference before writing any code.

FinStack is not just another CRUD application. It combines traditional software engineering with Artificial Intelligence and Machine Learning to help users make better financial decisions. Because multiple developers work on different modules simultaneously, maintaining consistency across the codebase is one of our highest priorities.

The purpose of this guide is to ensure that every team member:

• Understands the project architecture.
• Follows the same coding standards.
• Uses Git correctly.
• Builds features without affecting other modules.
• Produces code that is maintainable and easy to extend.

If every developer follows this guide, new features can be added with minimal conflicts, the application will remain scalable, and future contributors will be able to understand the project without extensive hand-holding.

# 2. Project Vision

## Why FinStack Exists

Managing personal finances has become increasingly complex. Users often rely on multiple applications to track expenses, understand investments, read financial news, calculate taxes, evaluate loans, and monitor their financial health.

Our vision is to bring these capabilities together into one intelligent platform.

Instead of forcing users to switch between multiple applications, FinStack aims to become a centralized AI-powered financial assistant capable of analysing financial data, explaining results in simple language, and helping users make informed decisions.

The focus of the project is not only automation but also education. Every recommendation generated by the platform should be understandable to the user.

Instead of displaying:

    Financial Score: 72

the platform should explain:

    Your financial score improved because your savings ratio increased by 15% while your monthly liabilities remained stable.

This philosophy applies to every module developed within the project.

# 4. Development Philosophy

Every technical decision in FinStack follows four core principles.

## 1. Modularity

Every feature should exist as an independent module.

For example, SmartFeed should never contain Financial Health logic.

Likewise, the Financial Health Analyzer should not directly manipulate SmartFeed data.

Each module should solve one problem well.

This separation makes testing, maintenance, debugging, and future development significantly easier.

---

## 2. Separation of Responsibilities

A single file should have a single responsibility.

Examples:

router.py

Only receives HTTP requests and returns responses.

service.py

Contains business logic.

model.py

Defines database models.

schema.py

Validates incoming and outgoing data.

Keeping responsibilities separated makes debugging significantly easier because developers immediately know where a particular piece of logic belongs.

---

## 3. Scalability

Whenever implementing a feature, ask yourself:

"If this feature becomes ten times larger in six months, will this architecture still work?"

If the answer is no, reconsider the implementation.

Temporary shortcuts often become permanent technical debt.

---

## 4. Consistency

Two developers working on different modules should still produce code that looks like it was written by the same team.

Consistency is more valuable than individual coding preferences.

Follow the project conventions instead of personal preferences.

# 6. Repository Structure

One of the primary goals of FinStack is to remain maintainable even as new features and developers are added. To achieve this, the project follows a modular architecture where each module is responsible for a single domain.

A developer should be able to locate any file within a few minutes without searching through hundreds of unrelated folders.

The project is divided into two major parts:

• Frontend
• Backend

Both have their own responsibilities and should remain independent of each other.

The frontend should never contain business logic, database queries, or machine learning code.

Similarly, the backend should never contain UI-specific logic.

The backend communicates with the frontend through REST APIs.

The overall project structure is shown below.

```
FinStack/
│
├── frontend/
│
├── backend/
│
├── docs/
│
├── README.md
│
├── .gitignore
│
└── requirements.txt
```

## Backend Structure

The backend follows a feature-based architecture.

```
backend/
│
├── common/
│
├── modules/
│
│   ├── financial_health/
│   │
│   ├── smartfeed/
│   │
│   ├── auth/
│   │
│   └── document_upload/
│
├── ml/
│
├── main.py
│
└── config.py
```

Rather than organizing the backend by file type (controllers, models, routes, etc.), FinStack organizes the backend by feature.

This means that everything related to SmartFeed exists inside the SmartFeed module.

Everything related to Financial Health exists inside the Financial Health module.

This approach has several advantages:

• Modules are independent.
• Features can be developed in parallel.
• Merge conflicts are significantly reduced.
• Debugging becomes easier.
• New developers immediately know where feature-related files are located.

This architecture also makes it easier to convert individual modules into microservices in the future if required.

# 8. Git Workflow & Branching Strategy

Version Control is one of the most important aspects of collaborative software development. A poorly managed Git workflow can quickly lead to merge conflicts, overwritten code, unstable releases, and hours of wasted debugging.

To avoid these problems, FinStack follows a structured branching strategy where each branch has a specific purpose. Developers must understand not only *how* to use Git, but *why* each branch exists.

The objective is simple:

- Keep production code stable.
- Allow multiple developers to work simultaneously.
- Reduce merge conflicts.
- Ensure every feature is reviewed before integration.

---

# Current Branch Structure

```
                         main
                          │
                Production Ready Code
                          │
                    develop
                          │
        ┌─────────────────┴──────────────────┐
        │                                    │
   hk_develop                    Feature Branches
                                         │
                 ┌───────────────────────┴──────────────────────┐
                 │                                              │
      feat/financial-health                      feat/smartfeed
```

Each branch has a clearly defined responsibility.

---

## Main Branch

```
main
```

The **main** branch represents the most stable version of the application.

This branch should always be deployable.

Only thoroughly tested and reviewed code should reach this branch.

### Rules

✔ Stable code only

✔ Fully tested features only

✔ No experiments

✔ No incomplete modules

✔ No debugging commits

Developers should **never commit directly** to `main`.

---

## Develop Branch

```
develop
```

The **develop** branch acts as the integration branch.

Once individual feature branches are completed and reviewed, they are merged into `develop`.

This branch contains features that are complete but may still undergo integration testing before being promoted to production.

Think of `develop` as the staging area for the next release.

---

## hk_develop Branch

```
hk_develop
```

This branch belongs to the project lead.

Its purpose is to perform architectural changes, integration work, and major refactoring before merging into `develop`.

Examples include:

- Project restructuring
- Shared utility improvements
- Authentication integration
- Database migrations
- Repository cleanup
- Build fixes

Other developers should avoid making commits to this branch unless specifically instructed.

---

## Feature Branches

Feature branches are where day-to-day development takes place.

Examples:

```
feat/smartfeed

feat/financial-health
```

Each feature branch should represent **one functional module**.

Developers working on SmartFeed should work exclusively inside:

```
feat/smartfeed
```

Similarly, developers working on the Financial Health Analyzer should remain inside:

```
feat/financial-health
```

This isolation prevents unfinished work from affecting unrelated modules.

---

# Why Feature Branches?

Imagine two developers editing the Dashboard page simultaneously.

If both developers work directly on the `develop` branch, every commit has the potential to overwrite the other's work or introduce unexpected bugs.

With feature branches:

```
Developer A
        │
        ▼
feat/smartfeed

Developer B
        │
        ▼
feat/financial-health
```

Both developers can work independently.

Only after completing their module is the code merged into `develop`.

This dramatically reduces merge conflicts and keeps unfinished features isolated.

```text
Final
```

Push your changes.


Frequent pushes create remote backups and simplify collaboration.

# Merge Conflicts

Merge conflicts are a natural part of collaborative development.

They occur when two developers modify the same lines of code.

If a merge conflict occurs:

1. Pull the latest changes.
2. Read the conflict carefully.
3. Understand both versions.
4. Keep the correct implementation.
5. Test the project.
6. Commit the resolved conflict.

Never blindly accept one side of a merge conflict without understanding the consequences.

# 9. Backend Architecture

The backend of FinStack follows a **Feature-Based Modular Architecture**. Every business feature is developed independently while sharing common utilities through the `common` package.

The objective of this architecture is to:

- Reduce code coupling.
- Allow multiple developers to work in parallel.
- Improve maintainability.
- Simplify debugging.
- Make future expansion easier.

## Backend Directory Structure

```
backend/
│
├── common/
│   ├── database.py
│   ├── logger.py
│   ├── auth.py
│   ├── exceptions.py
│   └── utils.py
│
├── modules/
│   ├── auth/
│   ├── financial_health/
│   ├── smartfeed/
│   └── document_upload/
│
├── ml/
│   ├── training/
│   ├── inference/
│   ├── models/
│   └── datasets/
│
├── config.py
├── main.py
└── requirements.txt
```

## Module Structure

Every module should follow the same internal organization.

```
smartfeed/

router.py
service.py
schema.py
model.py
repository.py
utils.py
```

### router.py

- Defines API endpoints.
- Performs minimal request handling.
- Delegates business logic to services.
- Returns HTTP responses.

### service.py

Contains all business logic.

Responsibilities include:

- Processing requests
- Calling repository functions
- Running recommendation algorithms
- Calling ML models
- Returning processed results

Business logic must never be placed inside routers.

### schema.py

Contains Pydantic models for:

- Request validation
- Response validation

Never accept raw request data without validation.

### model.py

Contains database models.

Responsible only for representing database entities.

### repository.py

Handles all database operations.

Responsibilities:

- Insert
- Update
- Delete
- Query

Never write SQL queries directly inside service.py.

---

## Request Flow

```
React Frontend
        │
        ▼
FastAPI Router
        │
        ▼
Request Validation
(schema.py)
        │
        ▼
Business Logic
(service.py)
        │
        ├────────► Database
        │
        ├────────► ML Model
        │
        └────────► External APIs
        │
        ▼
Response
        │
        ▼
React Frontend
```

This separation ensures every layer has one responsibility.

- Return meaningful values.

Comment WHY.

Not WHAT.

Bad


Good

```python

```

---

## Error Handling

Never ignore exceptions.

Bad


Good

```python

```

---

## Logging

- Errors
- Warnings
- Important operations

Do not log passwords, API keys, or sensitive user data.
